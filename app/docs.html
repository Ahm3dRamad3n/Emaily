Introduction

Emaily receives form submissions through one public endpoint, renders them into an HTML template you've defined, and sends the result through an email account you've connected — Gmail, Outlook, SendGrid, Resend, or plain SMTP.

Three things make up every project: a service (the account that actually sends), a template (the HTML and routing rules), and an access mode (how strictly the submit endpoint checks who's calling it).

Quick Start

01

Register and create a project

Create an account, then create a project from your dashboard. Every project gets its own pub_ and sec_ key pair.

02

Connect a sending service

From the project's Services tab, connect Gmail or Outlook through OAuth, add a SendGrid or Resend API key, or add any SMTP account with an app password.

03

Create a template

Write the HTML body with {{variable}} placeholders for whatever fields your form collects, set a subject line, and pick which connected service should send it.

04

Configure the access mode

Decide whether the project accepts calls from a browser (FrontendOnly, checked against your allowed domains), from a backend only (BackendOnly, requires the private key), or both (Hybrid).

05

Submit your first email

POST to your project's submit endpoint with the template ID and your field values.

curl -X POST \ https://BASE-URL/submit/pub_9f2a... \ -H "Content-Type: application/json" \ -d '{"templateId":"t_contact_form","fields":{"name":"Sara","message":"Hi!"}}'

Access modes

Every project is set to exactly one of three modes, which changes what the submit endpoint requires:

Mode Private key required? Origin checked? Typical use
FrontendOnly Must not be sent Yes, against your allowed domains A form embedded directly on a website
BackendOnly Required, must match Not checked Server-to-server calls only
Hybrid Optional Checked only when no private key is present Supporting both a public form and a backend integration

Change a project's mode any time from its settings — see the API reference for the exact request.

Templates & variables

A template's HTML can reference any field from the submitted payload using double curly braces:

<h1>New message from {{name}}</h1> <p>{{message}}</p>

Submitting {"fields":{"name":"Sara","message":"Hi!"}} against that template fills both placeholders before sending. The rendered HTML is sanitized after substitution, so a field value can't inject markup into the final email.

Each template also has its own reply-to, CC, and BCC settings, an optional reCAPTCHA or App Check requirement, an optional auto-reply template, and a Save to history toggle — switching that off means the payload and rendered HTML for its submissions are never stored.

Submitting programmatically

The submit endpoint accepts a plain JSON POST from any language. From JavaScript:

fetch("https://BASE-URL/submit/pub_9f2a...", { method: "POST", headers: { "Content-Type": "application/json" }, body: JSON.stringify({ templateId: "t_contact_form", fields: { name: "Sara", message: "Hi!" } }) }) .then((res) => res.json()) .then((data) => console.log(data));

A successful call returns 202 Accepted. Full field-by-field detail is in the API reference.

Logs & retries

Open History in your dashboard and pick a project to see every submission, each with a status — Pending, Sent, Failed, Resent, Discarded, or QuotaExceeded. Opening one shows the original payload, the rendered HTML, and any error message, unless the template that produced it had history-saving turned off.

A submission with status Failed can be retried directly from its detail view, which re-queues it for delivery.

Integrations

After a successful send, a project can also be configured to:

  • Post a delivery notification to a Telegram chat.
  • Append a row — timestamp, project, recipient, subject, and status — to a Google Sheet.
  • Generate an AI summary of the email and attach it to the submission record.
